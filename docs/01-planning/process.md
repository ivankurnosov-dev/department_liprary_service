# Процесс команды и рабочее соглашение

## 1. Выбор методологии
Выбранная методология: **Kanban**. 
*Обоснование:* Так как команда состоит из одного человека, Scrum с его фиксированными спринтами и ролями (Scrum Master, Product Owner) избыточен. Kanban позволяет сфокусироваться на непрерывном потоке (согласно концепции Continuous Flow) и минимизировать время простоя, что идеально подходит для индивидуальной разработки.

## 2. Доска задач и WIP-лимиты
Настроена доска в GitHub Projects со следующими колонками:
1. **Backlog:** Все неприоритетные или не до конца описанные истории.
2. **Ready:** Задачи, готовые к разработке.
3. **In Progress (WIP = 1):** Задача, которая пишется в данный момент.
4. **Review & CI (WIP = 1):** Проверка кода через Pull Request и автотесты.
5. **Done:** Завершенные задачи.

*Обоснование WIP-лимитов (Закон Литтла):* Lead Time = WIP / Throughput. Чтобы минимизировать время выполнения задачи (Lead Time) при пропускной способности (Throughput) около 2 историй в неделю, WIP-лимит в колонке "В работе" строго равен 1. Это исключает потери времени на переключение контекста.

## 3. Definition of Ready (DoR)
Задача готова к перемещению в колонку "Ready" и взятию в работу, если:
* Понятна суть пользовательской истории.
* Описаны минимум 2 критерия приёмки в формате BDD (Дано / Когда / Тогда).
* Задача имеет оценку трудоемкости.

## 4. Definition of Done (DoD)
Задача считается выполненной (перемещается в "Done"), если:
* Код написан, собирается без ошибок и локально протестирован.
* Изменения оформлены через ветку и Pull Request, привязанный к номеру Issue.
* CI-конвейер успешно пройден (в будущих ЛР).
* Pull Request влит в `main`.

## 5. Рабочее соглашение (Team Agreement)
Так как проект выполняется индивидуально, соглашение регламентирует внутреннюю дисциплину:
* **Синхронизация:** Актуализация статусов задач на доске перед началом каждого сеанса разработки.
* **Правила ветвления:** Прямые коммиты в ветку `main` запрещены. Вся работа ведется в ветках вида `feature/issue-X`.
* **Ревью:** Обязательное самостоятельное код-ревью в интерфейсе Pull Request на GitHub перед слиянием.
